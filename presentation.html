“YOLO only handles one image at a time”

Not a YOLO limitation — three bugs almost every naive FastAPI model wrapper has.

Bug 1

Blocking the event loop

async def predict(...):
    model.predict(image)
    # blocking, 150 ms

Runs on the loop thread → the process can't accept, parse or answer anything else. Not even /healthz.

Bug 2

Shared model isn't thread-safe

model = YOLO(...)  # ONE instance
def _infer(img):
    model.predict(img)

Reuses a mutable internal predictor. Threads overwrite each other → image A's results for image B.

Bug 3

CPU oversubscription

# torch is already parallel
4 workers × N threads
        on 2 cores

Threads thrash → everything slower → people conclude "parallelism doesn't help" and revert.

Bug 2 is the dangerous one. It doesn't crash and it doesn't log — it silently returns wrong answers under load. You'd find out in production.
Container gotcha: os.cpu_count() reports the host's cores, not the ACA limit. Never auto-size a pool from it.

The fix

All in app/main.py — same pattern for both models.

1 · Startup — build N models + N threads 
torch.set_num_threads(TORCH_THREADS_PER_WORKER)  # =1

pool = queue.Queue()
for _ in range(INFERENCE_WORKERS):
    m = YOLO(MODEL_NAME)
    m.predict(warm)          # warm each one
    pool.put(m)

executor = ThreadPoolExecutor(
    max_workers=INFERENCE_WORKERS)
2 · Endpoint — never block the loop 
raw = await file.read()

loop = asyncio.get_running_loop()
result = await loop.run_in_executor(
    executor, _infer, image)
3 · Borrow / return a model 
def _infer(image):
    model = pool.get()     # exclusive
    try:
        return model.predict(image)
    finally:
        pool.put(model) # always
4 · ACA scale rule = pool size 
--scale-rule-http-concurrency $InferenceWorkers
--min-replicas 0 --max-replicas 10

A replica accepts exactly what it can genuinely run. The moment it would queue, KEDA adds a replica.

One invariant makes it safe:
executor threads == pool size
At most N threads inside _infer, exactly N models → pool.get() never waits, and no two threads can ever share a model.

A trap worth showing

Our first OCR run reported 21/24 wrong. It was the test that was wrong:

image 0:  expected 'CODE0000' → got 'CODEOOOO'
image 7:  expected 'CODE0007' → got 'CODEOOO7'
image 22: expected 'CODE0022' → got 'CODEOO22'

Every answer belonged to its own image — EasyOCR just read 0 as O.

Lesson: assert on identity (which input produced this?), never on model accuracy.

Why the difference? Look at inference_ms. For OCR it stays flat → the second worker used genuinely idle CPU. For YOLO it inflates → a single yolov8n pass already saturates both cores, so you're just splitting CPU.
Rule: the slower and less CPU-saturating one inference is, the more a second worker pays.

What to remember

Engineering rules

  • Never run blocking inference inside async def.
  • High-level wrappers (YOLO, EasyOCR, PaddleOCR, HF pipeline) are not thread-safe → one instance per worker.
  • Low-level engines (ONNX Runtime, bare torch.no_grad) are → share and tune threads instead.
  • Keep scale rule == pool size.
  • Measure inference_ms at 1 vs N workers before choosing N.
