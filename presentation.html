The symptom

“YOLO only handles one image at a time”

A real customer observation — and it is not a limitation of YOLO.

It's caused by three independent bugs that almost every naive FastAPI model wrapper contains. Two of them cost throughput. One of them silently returns wrong answers.

Bug 1

Blocking the event loop

Throughput pinned to 1 request. Even /healthz stops answering.

Bug 2

Model isn't thread-safe

Image A's results returned for image B. No error raised.

Bug 3

CPU oversubscription

Makes the "fix" look useless, so people revert it.

Bug 1

Blocking the asyncio event loop

This is what everyone writes first.

Broken 
@app.post("/predict")
async def predict(file: UploadFile):
    ...
    results = model.predict(image)
    # blocking, CPU-bound, ~150 ms
    return results

async def runs the handler on the event loop thread. predict() never yields, so for 150 ms the process cannot accept, parse or answer anything.

Fixed 
raw = await file.read()   # async I/O is fine

loop = asyncio.get_running_loop()
result = await loop.run_in_executor(
    state["executor"], _infer, image)

The CPU work moves to a worker thread; the loop stays free to accept more requests.

Side effect people miss: health probes time out under load, so ACA restarts perfectly healthy replicas. It looks like random instability.
Bug 2 — the dangerous one

A YOLO object is not thread-safe

Now that requests run on threads, the obvious next step is wrong.

Broken 
model = YOLO(MODEL_NAME)   # ONE shared instance

def _infer(image):
    return model.predict(image)
    # data race across threads

A YOLO instance lazily creates and reuses an internal model.predictor holding mutable per-call buffers. Two threads overwrite each other.

Fixed — one instance per worker 
pool = queue.Queue()
for _ in range(INFERENCE_WORKERS):
    pool.put(YOLO(MODEL_NAME))

def _infer(image):
    model = pool.get()      # borrow
    try:
        return model.predict(image)
    finally:
        pool.put(model)  # always return
Why this one matters most: it doesn't crash and it doesn't log. It silently returns the wrong detections under load — you'd only find out in production. easyocr.Reader has exactly the same problem.
Bug 3 — the subtle one

CPU oversubscription

The reason people try threading, see no gain, and conclude “it doesn't work”.

PyTorch is already internally parallel: one predict() spreads its matrix maths across every core it can see. Run 4 workers on a 2-core container and you get 4×N threads fighting over 2 cores — every request slows down while throughput barely moves.

torch.set_num_threads(TORCH_THREADS_PER_WORKER)   # default 1

# keep:  workers × threads  ≤  container vCPU
Container gotcha: os.cpu_count() inside a container reports the host's cores, not the ACA limit. Never auto-size your pool from it — the deploy script passes INFERENCE_WORKERS explicitly.
The fix, in full

Four pieces of code

All in yolo-demo/app/main.py — the OCR demo is identical bar the model class.

1 — startup 
torch.set_num_threads(TORCH_THREADS_PER_WORKER)

pool = queue.Queue()
for _ in range(INFERENCE_WORKERS):
    model = YOLO(MODEL_NAME)
    model.predict(warm, verbose=False)  # warm it
    pool.put(model)

state["executor"] = ThreadPoolExecutor(
    max_workers=INFERENCE_WORKERS)
2 — endpoint never blocks 
raw = await file.read()
image = Image.open(io.BytesIO(raw)).convert("RGB")

loop = asyncio.get_running_loop()
result = await loop.run_in_executor(
    state["executor"], _infer, image)
3 — borrow / return 
def _infer(image):
    model = state["pool"].get()
    try:
        return model.predict(image, verbose=False)
    finally:
        state["pool"].put(model)
4 — ACA scale rule 
--scale-rule-type http `
--scale-rule-http-concurrency $InferenceWorkers `
--min-replicas 0 --max-replicas 10

Scale rule equals pool size, so a replica only ever accepts what it can genuinely run.

The whole trick is one invariant: executor threads == pool size. At most N threads can be inside _infer, and there are exactly N models — so pool.get() never waits and no two threads can share a model.

The insight to take away

Why did OCR gain 90% and YOLO only 20%?

Look at inference_ms

Model1 worker2 workersVerdict
YOLO yolov8n162 ms198 msinflated
EasyOCR2350 ms2350 msunchanged

If per-inference time stays flat, the extra worker used genuinely idle CPU — real parallelism. If it inflates, you're just splitting the same CPU.

Why they differ

  • YOLO is one big, well-parallelised convolution stack — a single forward pass already keeps both cores busy.
  • EasyOCR has long sequential phases (detect → crop → recognise) with limited matrix parallelism, leaving cores idle.
Rule of thumb: the slower and less CPU-saturating a single inference is, the more in-replica parallelism pays. Measure inference_ms at 1 vs N workers before choosing.

Configuration

Align the pool with the scale rule

scale-rule concurrency  =  INFERENCE_WORKERS
ConfigurationWhat happens
Rule > workers
rule 10, workers 2		 Replica accepts 10 concurrent but runs 2. The other 8 pile into queue_wait_ms; latency balloons and ACA never scales out — the replica looks like it's coping.
Rule < workers
rule 1, workers 2		 ACA adds replicas while each existing one is half idle. You pay for unused CPU.
Rule = workers A replica takes exactly what it can genuinely run in parallel; the moment it would queue, KEDA adds a replica.

Capacity

max concurrent = INFERENCE_WORKERS × maxReplicas
= 2 × 10 = 20

The simple alternative

“One replica per inference” is a perfectly valid design — simplest mental model, no in-process threading at all.

“But YOLO uses lots of RAM”

Measured memory, not guesses

From rss_mb in /stats — what ACA counts against the limit.

YOLO (yolov8n)OCR (EasyOCR)

Baseline, 2 workers427.4 MB576.6 MB

Three very different terms

  • Fixed runtime (~424 MB torch + OpenCV) — dominates, paid once.
  • Weights × N — the part people fear; for a nano model it's negligible.
  • Activations × concurrency — the real per-request cost, and it exists whether you pool or not.

So: can you run several in one replica?

Yes. On 4 GiB, YOLO has room for ~100 concurrent inferences, OCR ~15–20.

CPU binds long before RAM for both models — which is exactly why INFERENCE_WORKERS = 2 on 2 vCPU is the right call.

This flips for large models: a 2nd yolov8x costs ~272 MB; a 2nd 7B LLM costs ~14 GB — there you share the model and scale out instead.

Things that will bite you

Three findings worth showing

Gotcha 1

ACA drops in-flight connections while adding replicas

No client retries63 requests lost
2 connection-level retries200 / 200 succeeded

Transport errors, not HTTP 5xx — the app logged nothing. Retry connect only (read=0), so a request that actually reached the model is never silently repeated. Demo it with bench.py --retries 0.

Gotcha 2

Our own OCR test reported 21/24 failures — and was wrong

image 0:  expected 'CODE0000', got 'CODEOOOO'
image 7:  expected 'CODE0007', got 'CODEOOO7'
image 22: expected 'CODE0022', got 'CODEOO22'

Every answer belonged to its own image — EasyOCR just read 0 as O. Glyph ambiguity, not a threading bug.

Lesson: assert on identity (which input produced this result?), never on model accuracy — otherwise you'll chase a threading ghost that doesn't exist.
Gotcha 3

A shared requests.Session caps at 10 connections

Above that it throws SSLEOFError — which looks exactly like a server fault. Use one session per thread. This cost us a debugging cycle.

Running it live

Demo script

Order of the story

  1. Correctness first — 24 images, all correct. Parallelism is safe.
  2. Scale to zero — 0 replicas, one request, show the cold start.
  3. Saturate one replica — queue_wait_ms grows, inference_ms flat.
  4. The bug — WORKERS=1: peak_running stuck at 1.
  5. The fix — WORKERS=2: peak_running = 2, p50 collapses.
  6. The caveat — throughput only +20% on YOLO. Segue to scale-out.
  7. Scale out — replicas 1→10, RPS 5.9→27.
  8. The rough edge — --retries 0 drops requests.

Wrap-up

What to remember

The engineering

  • Never run blocking inference inside async def.
  • High-level model wrappers (YOLO, EasyOCR, PaddleOCR, HF pipeline) are not thread-safe — one instance per worker.
  • Low-level engines (ONNX Runtime, bare torch under no_grad) are — share and tune threads instead.
  • Cap torch threads; never size a pool from os.cpu_count() in a container.
  • Keep scale rule == pool size.
